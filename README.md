## Lab Activity Instance 0

- Lab 1: Discussion
 Ephemeral State (Counter) vs App State(Light/Dark mode)
  - For this lab, I learned that state management in Flutter usually falls into two categories: ephemeral (local) state and app (global) state. I use the built-in "setState" method for ephemeral state, which is great when the data only matters to a single, isolated widget, like my localized counter. Whenever I call "setState", it tells Flutter to rebuild only that specific widget's UI. This is super efficient, but I found that it doesn't scale well; if I try to pass this local data down to other screens, I have to pass it through every constructor, which is called "prop drilling" and gets really messy. On the other hand, I used "Provider" to manage my app-wide global state, like my dark/light mode theme. By moving the logic into a separate model class with "ChangeNotifier" and wrapping my app in a "ChangeNotifierProvider", I can easily grab or change that shared data from anywhere in my app. When I call "notifyListeners()", it automatically rebuilds any widget listening to it, which completely solves the prop drilling issue even though it takes a little more setup code.

- Lab 2: Discussion
  - For this lab, I learned how to build an asynchronous data-driven mobile application by establishing a clean interaction between the model, service, and screen layers to render API endpoints. The process begins with the service layer "ProductService", which is responsible for HTTP network communication with the remote API endpoint. It executes requests, handles network exceptions like converting "localhost" to "10.0.2.2" for Android emulators, and receives raw JSON response bodies. Once received, the service passes this data to the model layer "ProductModel", which handles JSON deserialization via factory constructors like "Product.fromJson". The model enforces strict type safety, maps nested data structures, and provides fallback values to ensure the app never crashes due to unexpected or null JSON data. Finally, the UI layer "ProductScreen" invokes the service method and uses a "FutureBuilder" to dynamically react to data states—rendering a loading spinner while fetching, displaying retry controls on failure, or displaying an interactive grid of products when successful. Clicking a product card passes the parsed model instance to the "ProductDetailScreen" to display complete item specifications. This activity introduced the Service-Oriented Architecture and Repository Design Pattern based on the Separation of Concerns principle. By separating network operations, data models, and UI widgets into distinct layers, the application avoids monolithic code, adheres to the Single Responsibility Principle, and enables unit testing through dependency injection.

- Lab 3: Discussion
  - For Lab Activity 3 I am going to assume that the interaction between my cart model, services and screens is pretty simple. First, my Cart Model is a pattern which converts the unorganized JSON data that I receive from the API into organized Dart objects, so that my app can consume something such as product ID, price etc. My Cart Service then takes over the grunt work and sends a GET request to the API, retrieves the data and passes it into my model which formats it into a list. Lastly, the Cart Screen displays the actual items that the user sees, using a FutureBuilder to wait for the service to complete fetching the data until the items are shown. The cool part is that when I tap on something in the cart, it displays the screen grabs of that specific item's ID and forwards it to my ProductService to load the full details of that item and then directly to detail_screen.dart. This is super-efficient, since I can send both the main shop screen, and the cart screen to the exact same detail screen, and I don't have to code the UI twice for each – that's super-efficient. I used the Separation of Concerns a lot in this activity by following the MVC or Service Oriented approach. This helps me keep my code much tidier and easier to trace as my business rules go into the Model, my network calls go into the Service and my UI rendering goes into the Screen. Finally, if I wish to retrieve a particular user's cart rather than all the carts in the database I will use the getById method through the URL parameters. I do not invoke the base /carts endpoint instead I send an ID into my service function, and it then appends an ID to the end of the URL (such as /carts/user/30). If I send a GET request to that URL, the API can identify what I'm requesting, and only return the JSON data of that specific user, which saves bandwidth and speeds up my App's loading time.

- Lab 4: Discussion
  - The interaction between my user model, services and screens in Lab Activity 4, is pretty cool. First, my User Model converts the user's information from the JSON API (such as their name, email, avatar) to Dart objects. The UserService takes care of fetching these details from the app by sending a POST request to authenticate the user, and the UserService stores them locally using SharedPreferences. When I hit the Profile Screen the only thing I have to do is ask the UserService for this saved data, and create the UI with a FutureBuilder. That way, the screen doesn't have to make a brand new network call to retrieve the data I saved, it just accesses the data I saved! From a design point of view, I expanded on my Separation of Concerns (MVC) pattern in this post by adding persistent local storage. The separation of the authentication logic and also the handling of SharedPreferences is done entirely in the UserService, which leaves my UI screens entirely clean as well as concentrates on displaying the data. Finally, all the saved user data is important to me for rendering my Cart Screen. I removed a hardcoded user ID from my Cart Screen that I was using to retrieve the cart and instead asked the UserService for the user id of the currently logged in user. Then sends that particular ID to the CartService to get just my cart items. This makes the app truly personalized and dynamic!

- Lab 5: Discussion
 - In Lab Activity 5, I devised and compared two ways to authenticate users: DummyJSON and Firebase Authentication. DummyJSON does not register any users, it just pretends to register them by simulating a POST request to /users/add. Unlike Firebase, registerUserToFirestore is not registered in the cloud and creates real and persistent accounts in Firestore. I had to save a static token in SharedPreferences by myself and DummyJSON returned it to me when I signed in. I don't even have to concern myself with keeping sessions alive, refreshing tokens, real-time tracking of the authenticated state with authStateChanges, etc., because Firebase takes care of it for me.

- I have mostly implemented the Service pattern in the UserService implementation. The concept was to separate the authentication logic from the UI as to not require screens to know what provider is being utilized. UserService is a single place everyone can access for DummyJSON and Firebase, it checks the loginType ('firebase' or 'dummyJson') and determines the behavior of the getUserData() method accordingly. I also included ValueNotifier to make sure that the UI updates when the auth object changes state but doesn't need to refresh things if the state changes.

- The greatest advantage to using Firebase in this application is the fact that you don't have to create fake accounts since you are dealing with real accounts. It also provides complete control over the user lifecycle, such as updating display names, changing passwords, deleting accounts and much more: token security is taken care of in the background, and auth state is synced in real time across devices.
